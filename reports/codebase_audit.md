# Comprehensive Codebase & Evaluation Audit Report

## Executive Summary

This audit evaluates the **Brand-Aware AI Customer Support Agent** (`hiver-sde-ai-support-agent`) codebase, data pipeline, baseline models, retrieval mechanism, evaluation harness, safety policy engine, and reported results.

---

## 1. Current Architecture

- **Data Processing**: Loads Kaggle `twcs.csv` (2.8M rows), extracts `AmazonHelp` tweets (169k replies / 42k sampled threads), normalizes URLs/mentions, and reconstructs multi-turn customer-agent threads into clean JSONL records (`conversations_AmazonHelp.jsonl`).
- **Dataset Partitioning**: Conversation-level grouping into 70% Train, 15% Validation, and 15% Test splits (`data/splits/`).
- **Intent Classifier**: LLM-based intent classifier supporting OpenAI, Gemini, and a rule-based Mock fallback (`src/intent_classifier.py`).
- **Historical Retrieval**: Local FAISS vector index built on `sentence-transformers` (`all-MiniLM-L6-v2`) embeddings of training customer messages (`data/index/`).
- **Grounded Response Generation**: LLM response generator constrained by top retrieved historical brand resolutions (`src/response_generator.py`).
- **Escalation Policy Engine**: Multi-gate deterministic safety engine (`src/escalation.py`) requiring confidence >= 0.80, similarity >= 0.45, known intent, grounded evidence, and non-sensitive category status to permit `AUTO_HANDLE`.

---

## 2. Explanation of the 100% LLM Intent Classifier Result

The initial evaluation report indicated **100.00% Accuracy** and **1.0000 Macro F1** for the LLM Intent Classifier when evaluated in offline `mock` mode.

### Root Cause Analysis:
1. **Circular Heuristic Match in Mock Mode**: In `src/dataset_split.py`, silver intent labels (`silver_intent`) for the test set were generated using keyword regex rules (`assign_silver_intent`).
2. In `src/intent_classifier.py`, the `MockLLMClassifier` imported and executed the **exact same keyword regex rules** (`INTENT_KEYWORDS`).
3. As a result, in mock mode, `y_pred` was generated by the exact same python function as `y_true`, producing an artificial **100% match**.
4. **Resolution**: In real LLM inference mode (OpenAI / Gemini) or independent holdout evaluation with human-verified labels, the classification accuracy reflects true language model understanding.

## 3. Potential Data & Retrieval Leakage Points Identified

| Audit Item | Findings | Status / Action |
| :--- | :--- | :--- |
| **Conversation Leakage across Splits** | Conversation-level grouping was verified. `train.jsonl`, `val.jsonl`, and `test.jsonl` share 0 conversation IDs. | **No Leakage** (Verified) |
| **Golden Set in Splits** | All 176 golden candidates were sampled from `test.jsonl`. 4 short generic text duplicates (e.g. `"Hello"`) matched training set text. | **Fixed**: Added explicit deduplication & filtering in retrieval. |
| **Retrieval Query Self-Match** | Retrieval index is built strictly from `train.jsonl`. Evaluation queries from `test.jsonl` are not in the index. | **Verified**: Golden set excluded from index. |
| **Prompt Metadata Leakage** | Classification prompt receives only raw customer message and intent descriptions. No gold labels, expected actions, or hidden metadata are passed. | **No Leakage** (Verified) |
| **Cache Key Leakage** | `src/cache.py` uses `hashlib.sha256(model + prompt)`. No evaluation ground truth is included in cache keys. | **No Leakage** (Verified) |

---

## 4. Potential Metric & Evaluation Problems

1. **Over-reliance on Raw Accuracy**: Raw accuracy ignores class imbalance. Macro F1 (0.8718 on TF-IDF) and Auto-handling Coverage (17%) are the authoritative operational metrics.
2. **Mock Mode vs API Evaluation**: Evaluation scripts must clearly distinguish between offline Mock provider validation and live LLM evaluation.
